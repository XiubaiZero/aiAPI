把“能算”做成“能被验证”的 AI API 价格助手

2026 年 9 月 · 作者：XiubaiZero

这次项目的目标并不复杂：做一个能比较海外 AI API 价格、再按用户输入的 token 用量估算成本的小工具。但真正开始后，我发现最难的并不是做表格或写计算公式，而是让每一项结果都能被外部验证。最终项目包含 OpenAI、Anthropic 和 Gemini 三家供应商的九个文本模型；用户可以在“模型价格对比”页查看模型名称、供应商、上下文长度和输入/输出单价，也可以在“用量统计”页填入单次调用的输入 token、输出 token 与调用次数，查看各模型的总成本排序。

先确定边界，再开始写代码

一开始我差点把 LiteLLM 之类的聚合价格表作为数据源，因为它们覆盖广、格式统一，做起来会很快。但项目要求明确规定价格必须来自官方页面。聚合平台可以作为调研线索，却不能成为最终数据依据；它可能有更新延迟、不同计费层级混在一起，或者缺少原始查询日期。因此我改为只在数据中保存 OpenAI、Anthropic、Gemini 官方文档链接和北京时间查询时间，并写了更新脚本直接抓取官方页面。脚本的原则是“宁可失败，不猜价格”：只要有一家页面无法解析，就不覆盖上一次已验证的数据。

计算逻辑要让用户看得懂

用量计算没有调用模型，也没有把 token 数量当成总量。输入 token 数量和输出 token 数量都代表单次 API 调用的平均值，系统先乘以调用次数，再除以一百万并乘以对应单价。页面把输入成本、输出成本和总成本的公式都写出来，同时提供 200 输入 token、1,000 输出 token、100 次调用的动态示例。这样用户不仅能看到结果，也能手算核对，减少“计算器黑箱”的感觉。人民币金额使用中国人民银行最近可用的美元兑人民币中间价，只作为估算，不冒充供应商账单。

AI 帮我提速，也提醒我必须验证

AI 在页面结构、TypeScript 类型、公式测试和 GitHub Actions 配置上很有帮助，特别适合把一个需求迅速拆成可运行的最小版本。但 AI 的第一批建议也暴露了风险：它推荐的相似项目依赖 LiteLLM 数据，和官方数据源要求冲突；部分模型、价格和页面结构也不能凭记忆相信。我用官方链接、可重复运行的脚本、单元测试和一次手动触发的 Action 来验证，而不是把“看起来合理”当成完成。

上线不是终点

部署环节也出现了两个很实际的问题。第一次 Git 推送使用账户密码失败，因为 GitHub 已不支持这种方式；改用仓库限定、具有 Contents 与 Workflows 写权限的 Fine-grained Token 后才成功。第一次 Vercel 地址又跳转到 SSO 登录页，虽然我自己能看见，但未登录用户无法访问，不能算公网部署。后来关闭部署保护并核验三个路由均返回 200，才满足“可打开 URL”的要求。手机端还发现结果卡片的输入成本和输出成本重叠，于是把小屏幕布局改成纵向成本信息，并重新构建、提交、部署。

这次最重要的收获是：小工具的完成标准不是“本地页面很好看”，而是“别人打开链接、检查来源、改变输入后，仍能复现并理解结果”。

如果再给我八小时，我会补充模型版本筛选和更细的计费场景，例如缓存、Batch、长上下文和图像/音频定价；同时给官方页面解析增加快照与告警，避免供应商改版后只能等待人工发现。下一次我会更早建立“数据来源—解析—展示—验证”的链路，先让一条数据端到端跑通，再扩展模型数量。这个项目不追求覆盖所有 API，而是保证当前展示的标准文本 token 定价有来源、可更新、可解释。
